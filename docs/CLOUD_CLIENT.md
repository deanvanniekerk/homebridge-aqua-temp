# Cloud transport and session recovery

Issue #4 adds an internal `AquaTempClient`, independent of Homebridge and with no runtime dependencies. The platform does not instantiate it yet. All automated requests use synthetic local servers; this change makes no live account requests and enables no heater controls.

## Contract and evidence

The client's `read` accepts owned discovery, shared discovery (one explicit page), device status, or telemetry selectors. It validates the request and returns the validated envelope's `objectResult` as `unknown`. Device-profile work must validate that result and interpret sensors, availability and capabilities before exposing them to HomeKit. The client does not infer freshness from successful HTTP, discover pages automatically, or label compressor activity.

`write` accepts an array of absolute wire parameters and returns the server's envelope result. It validates and snapshots the wire shape only; it does not establish valid device ranges, modes, permissions, idempotence or physical completion. No Homebridge setter calls it. The unresolved profile/acknowledgment gates must be resolved before enabling controls. A failed dispatched write carries `deliveryUncertain: true`, including expiry, disconnect, timeout, cancellation, server errors and malformed acknowledgments. It is never replayed or automatically followed by login. The coordinator must reconcile its outcome; the transport does not claim that an acknowledgment confirms actuation.

The [preserved issue #2 investigation](https://github.com/deanvanniekerk/homebridge-aqua-temp/blob/cf07e8e/docs/PROTOCOL.md) is the independently observed protocol source. Its login and invalid-token fixtures establish:

- One verified origin: `https://cloud.linked-go.com:449`; no legacy fallback or refresh endpoint.
- JSON POST login at `/crmservice/api/app/user/login`, with `userName`, lowercase hexadecimal MD5 of the UTF-8 password, and `type: "2"`. MD5 is a vendor wire encoding, not a password-storage recommendation.
- The CRM envelope uses string `error_code`, boolean `isReusltSuc` (vendor spelling), and a required `objectResult`. Success requires code `"0"` and `true` together. Contradictory/missing fields are invalid responses. Unknown properties are ignored.
- Login requires nonempty `x-token`, `userId`, and `appId`; an optional `user_id` alias must agree. Tokens must be valid printable ASCII header values. Returned IDs are used rather than guessed. Authenticated calls send `x-token`, not `accessKey` or `sessionid`.
- Failure code `"-100"` is an observed invalid-session signal. Generic `"-1"` is **not** a verified credential or expiry code. The client neither matches vendor messages nor invents additional vendor error codes.

HTTP 401 on login is categorized as invalid credentials; HTTP 401 on an authenticated request is treated as an expired session. HTTP 403 is permission denial. These are conservative HTTP policies exercised with synthetic cases, not claims that these exact HTTP failures were observed on this device. A CRM `-100` on login triggers contention cooldown, not a guess about credentials.

## Bounds and recovery

| Boundary          | Policy                                                                                                                                                                                                                                                                                                                           |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request           | 10-second absolute deadline including response body; 64 KiB encoded request maximum; 1 MiB streamed response maximum; no redirects or automatic socket-level replay                                                                                                                                                              |
| Read operation    | 30 seconds total including authentication and retry waits; at most two transient retries; once expiry is seen, at most one renewal and one read replay, with no retries after that replay                                                                                                                                        |
| Write operation   | 8 seconds total including authentication and waits; at most one command request; no deferred command after a cancelled/expired caller                                                                                                                                                                                            |
| Shared login      | One in-flight attempt for the account, separately bounded at 10 seconds; no internal login retries. Each waiter has its own cancellation/deadline. Cancelling one waiter does not cancel a login another waiter may still need. A login with no remaining waiters can finish within its own bound, but sends no queued operation |
| Transient failure | Network/TLS failures, timeouts, HTTP 429 and 5xx use account-wide backoff starting at 5 seconds, doubling with up to 20% positive jitter, capped at 5 minutes                                                                                                                                                                    |
| Retry-After       | Honor positive delta seconds or future HTTP dates, including delays beyond 5 minutes. If a delay cannot fit the remaining operation budget, return the failure and remaining delay immediately; later operations honor that gate too                                                                                             |
| Recovery          | A successful authenticated response resets the exponential failure count. It does not cancel a still-active delay requested by another concurrent response                                                                                                                                                                       |
| Paused auth       | Confirmed invalid credentials or account-level permission denial prevents further authentication/requests until a new client is configured (reload/restart). Device-specific status, telemetry or command permission denial is returned to its caller without invalidating other devices                                         |
| Contention        | A replayed read expiring again, three distinct current-session invalidations in 60 seconds, or expiry returned by login triggers a 5-minute cooldown. Old-session failures do not invalidate a newer session. After cooldown a later caller can log in again                                                                     |
| Shutdown          | `close()` is terminal and idempotent: abort requests, backoff waits and shared login; reject callers and refuse later work. No network request or retry timer is scheduled after close                                                                                                                                           |

Contention thresholds are initial engineering policy, not a measured vendor token lifetime or proof of competition with the app. The error message suggests a dedicated shared account without asserting the cause. Invalid protocol data, unsupported HTTP statuses/redirects and unknown vendor errors are not retried within an operation. A future device profile owns offline and unsupported-capability errors; transport does not invent those from raw payloads.

`ClientOptions` allows shorter request/read/write bounds for callers/tests, never larger than the defaults. A clock boundary supplies monotonic epoch time, cancellable sleep and randomness for deterministic retry/cooldown tests. Real abort timers still enforce deadlines. Production origin is fixed; only literal IPv4/IPv6 loopback HTTP(S) origins are accepted as local test overrides. TLS verification remains enabled.

## Errors and diagnostics

Every expected failure is a `CloudError` with a closed category, fixed message, numeric `retryAfterMs`, and `deliveryUncertain`. No raw vendor message, URL, body, headers, token, password/digest, account ID or original error cause is retained. Client credential/session fields are ECMAScript-private and are never logged or persisted. This module has no logging, global exception handlers or process-exit behavior. Callers must catch its rejected promises; the Homebridge adapter will translate categories at its asynchronous entry points.

## Verification

`npm test` builds first, exercises the client against real local HTTP/TLS sockets, then checks the packed artifact and isolated Homebridge lifecycle. Synthetic server cases cover envelope/token validation, oversized/incomplete bodies, expiry races, credential and permission failures, rate limits, retry caps, redirects, TLS/network failures, cancellation, shutdown, ambiguous writes and input snapshotting. The injected clock advances backoff/cooldown without a real five-minute wait; short real deadlines exercise actual socket aborts. No real credentials or raw captures are used.

Node's [HTTP client](https://nodejs.org/api/http.html) and [AbortController](https://nodejs.org/api/globals.html#class-abortcontroller) supply the underlying transport and cancellation APIs. This implementation is original and does not incorporate previous plugin code or tests.
