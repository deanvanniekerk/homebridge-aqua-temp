# Homebridge adapter checkpoint

The adapter implements the limited Heat profile in issue #7. The adapter uses the Homebridge-supplied HAP constructors, real dynamic-platform registration and cached accessory restore. It connects the actual client/gateway/coordinator for readings and supported controls. No previous plugin implementation or identity scheme was copied.

UUID input is the scoped package name, a `device` namespace and the stable normalized device ID. Owned/shared duplicates produce one accessory. Context contains only that ID and the local Celsius/Fahrenheit display preference. Cached readings are not trusted: handlers are installed during restoration and return communication failures until a fresh supported-profile reading arrives. Names and list positions do not define identity.

An empty `deviceIds` list selects all supported devices. A nonempty list excludes other identities; on launch, only recognized cached identities explicitly excluded by that list are unregistered. Cloud errors, temporary omissions and malformed cache identity never trigger removal. Removing the whole platform or migrating to a child bridge uses Homebridge's own cache lifecycle; this plugin does not edit unrelated caches.

Getters consult coordinator freshness and never initiate cloud traffic. Water values outside HAP's range or precision are rejected before HAP can silently clamp/round them. Target constraints intersect the verified device grid with the supported HAP grid; empty, malformed or unrepresentable constraints stay unavailable. Target Off/Heat reflects confirmed power/mode, while operating state requires a verified activity reading. Defrost, flow fault and unrepresentable operating states return communication failures. A target/temperature difference is never used to infer heating.

The supported profile exposes target writes from 15–38°C in 0.5°C steps: this is the intersection of the observed device range (15–40°C) and the supplied HAP range (10–38°C). A target set to 38.5–40°C in Aqua Temp remains unrepresentable in this Thermostat and returns a communication error; it is never rounded or clamped. Use the vendor app for those values. Off/Heat only controls power while the vendor mode is already Heat. Missing core readings or unsupported modes disable the advertised writes.

Idle is available when O07 is zero and the reported fault flag is clear. Positive compressor frequency remains unknown because heating and defrost cannot be distinguished. The current operating-state characteristic then returns a communication error while supported temperature and target-state handlers still work. Owner screenshots in #10 confirm that this error makes Apple Home mark the entire thermostat No Response and withhold its normal controls; the plugin does not fabricate heating to make a tile look healthy.

For a verified control contract, HAP setters validate supported values locally and delegate to the coordinator's eight-second queue/confirmation boundary. Timeout and busy conditions become the supplied HAP status errors. Display-unit changes only update the accessory's local context; temperatures and device settings remain Celsius. Startup, restore, recovery and shutdown never submit device-setting commands.

Tests use real HAP handlers and the actual coordinator with an explicitly synthetic control contract to check capability intersections, failed reads, command confirmation and timeout mapping. Platform lifecycle tests use the actual cloud client over local HTTP. The tarball test runs a production-only Homebridge 2.4.0 install with the real plugin and a test-host transport redirect, exercising real HAP HTTP reads, confirmed half-degree target and On/Off writes, and accepted-but-unconfirmed writes, cold/warm accessory identity, invalid config/recovery and child bridges. No routing configuration or helper is shipped in the package, and no real credentials are loaded. TLS verification is covered separately by the cloud transport tests.

The isolated process harness permits unauthenticated HAP reads on loopback and uses a synthetic PIN for writes. It must never run against a real Homebridge installation. Homebridge 2.4.0 has a five-second SIGTERM fallback in both its CLI and child process; a parent waiting on child IPC may exit with code 143 through that host fallback. The test records that known child-bridge exit path separately from the normal single-process exit 0, rejects crashes/restarts/forced SIGKILL, and checks plugin cancellation through the coordinator/gateway tests. These are bounded local process checks, not proof of physical iHost shutdown timing or long-run reliability.

There is also a HAP 2.2.2 presentation limitation: its `Characteristic.toHAP` catches getter errors when constructing `/accessories` discovery responses and substitutes the characteristic's default value. Ordinary `/characteristics` requests return the adapter's communication failure, as the process test verifies. Discovery values must not be interpreted as successful fresh reads, and this plugin does not patch Homebridge's serializer. Apple Home's handling of the initial discovery default versus subsequent read errors still needs the actual presentation checks in #10.
